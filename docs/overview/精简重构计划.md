# 精简重构计划

> 目标：在不破坏旧版对外契约的前提下，减少重构后新增的样板、重复边界和无效状态管理。
>
> 本文不是继续拆文件的计划。每个阶段都必须证明生产源码净减少；如果只是改善目录结构但增加总代码量，不计入精简收益。

## 1. 基线与判断

当前统计口径：只统计 `src/core`、`src/node`、`src/shared` 和 `client` 的生产源码，不把测试、文档、构建产物计入生产源码。

| 项目 | 当前基线 |
|---|---:|
| 旧版 `Waiting_refactored/src/node` | 约 6995 行 |
| 新版服务端生产源码 | 约 10633 行 |
| 新版服务端 + 测试 | 约 13000 行 |
| 当前测试 | 30 个套件通过，242 个断言通过 |

旧版 6995 行与新版 13000 行不是完全同一统计口径。新版增加的测试、安全处理、环境快照、上传和缓存迁移不能全部算作“重构冗余”。但新版服务端生产源码仍明显偏重，后续需要真实减重。

## 2. 已完成的精简

以下改动已经提交，不再重复实施：

- 复用公共 `sleep()`，删除 Registry 内重复工具。
- 删除多余的 Market HTTP 工厂包装和错误 `never` 类型。
- 抽取 Console 刷新适配。
- 统一纯转发 RPC 的 contract 校验和权限注册。
- 集中客户端市场、环境、Registry 查询 RPC。
- 合并 Installer 历史和详情读取的重复依赖构造。
- 删除市场服务基类未使用的任务缓存、错误缓存、`prepare()` 和 `collect()` 抽象。

已确认不采用的方案：

- `InstallerFacade + InstallerRuntime`：当前实现会同时保留公共门面和运行时方法，实测预计增加约 200 行，不符合精简目标。
- 所有缓存合并为万能 `Cache<T>`：数据语义不同，容易引入更多泛型选项。
- 为每个 Node API 都增加端口接口：会产生大量无实际替换价值的适配代码。

## 3. 精简原则

1. **生产源码必须净减少**：每个提交前统计变更前后行数，新增抽象代码必须由更大规模的删除抵消。
2. **公共契约不变**：RPC 名称和参数、DataService 通道、广播、HTTP 路由、磁盘格式和 `ctx.installer` public 方法不能无测试变更。
3. **优先删除无效状态和重复表达**：优先级高于移动文件和改名。
4. **复杂业务保持显式**：安装、快照传输、头像代理和竞速流程不强行表驱动。
5. **注释解释边界和原因**：只为生命周期、兼容性、竞态和安全约束加注释，不写逐行翻译代码的注释。
6. **小批次提交**：每个独立精简点单独提交，提交格式为 `refactor: 中文描述`；修复行为问题使用 `fix: 中文描述`。

## 4. 阶段计划

### P1：RPC 与适配样板收尾

状态：已完成，低风险范围收尾。

内容：

- 继续识别纯转发 listener，但只收敛不包含刷新、重试、快照和安装编排的 handler。
- 将客户端剩余的纯查询 RPC 迁移到 feature API。
- 删除重复的 `send(...) ?? Promise.resolve(...)`，但不为写操作引入弱类型包装。
- 统一重复的 Console refresh channel 列表。

本阶段收尾结果：删除重复的 `market/ensure-config` listener 注册，统一安装和配置流程的 Console 刷新调用；本阶段追加生产源码净减少 14 行。剩余 `send(...) ?? Promise.resolve(...)` 位于断线竞速、失败回退或头像容错路径，继续删除会改变无 socket 时的行为，暂不处理。

目标收益：生产源码净减少 **100～300 行**。

验收：RPC 契约测试、TypeScript、Biome、client build 全通过。

### P2：市场客户端状态单一化

状态：待开始，当前最高收益目标。

当前问题：市场数据同时存在于：

- `@koishijs/client.store.market`
- `client/market/state/snapshot.ts`
- `client/market/state/lookup.ts`
- `client/shared/sync/store-sync.ts`

目标结构：

```text
RPC / 广播
    ↓
MarketRuntimeStore（唯一业务状态源）
    ├── snapshot
    ├── lookup
    ├── registry
    └── registryStatus
    ↓
页面 / dialog / extension
    ↓
store.market（仅保留 Console 兼容投影）
```

执行顺序：

1. 先增加快照和 patch 乱序测试。
2. 新增 `MarketRuntimeStore`，初期继续同步旧 `store.market`。
3. 将 snapshot 和 lookup 改为读取 runtime store。
4. 删除 `store.market` 反向恢复 watcher。
5. 最后将页面和 extension 的直接 `store.market` 访问改为 selector。

目标收益：净减少 **200～500 行**，同时减少 watcher、版本判断和重复缓存。

禁止事项：在没有乱序、断线、重复 patch 测试前，不删除旧投影。

### P3：快照协议收敛

状态：待 P2 完成后开始。

统一 `snapshot`、`patch`、`lookup` 的版本语义，使用一个 revision：

```ts
interface MarketRevision {
    schema: 1;
    revision: number;
    generatedAt: number;
}
```

客户端规则：

- revision 小于等于当前值：丢弃。
- revision 连续：应用 patch。
- revision 跳跃：重新请求完整 snapshot。

目标收益：删除 `snapshotSuperseded`、重复 generation 和多处版本比较，净减少 **50～150 行**。

兼容策略：先新增字段并双读，完成宿主联调后再删除旧字段。

### P4：持久化状态原语

状态：待 P2/P3 完成后评估。

只提取两个小原语：

- `SingleFlight<Key, Value>`：合并同一资源的并发请求。
- `DebouncedAtomicWriter<T>`：延迟求值、原子写入、生命周期 flush。

优先复用范围：

- MarketDataStore
- market snapshot gzip task
- registry stats 写入
- PackageCache 任务去重

不统一业务缓存的 TTL、错误模型和磁盘格式。

目标收益：净减少 **100～250 行**。

### P5：安装流程状态机

状态：高风险，最后处理。

当前 `client/shared/install/install-flow.ts` 混合了：

- UI 显示状态
- 安装 RPC
- socket 断线
- 自更新
- fallback 重试
- 安装日志

只有在补齐以下测试后才开始：

- 正常安装成功/失败
- 自更新断线
- 非自更新断线
- fallback 可用/不可用
- 重试期间重复触发

目标不是拆文件，而是把隐式状态改为显式状态联合；如果代码量不减少，保留现状，不强行实施。

## 5. 暂不处理的区域

- `InstallerFacade + InstallerRuntime`：当前收益不足，除非出现不增加总代码量的实现。
- Registry 与 Market 的缓存完全合并：领域差异过大。
- 全部 Zod schema 移入 `shared`：会污染客户端运行时依赖。
- 删除 `ctx.installer` public 转发方法：会破坏兼容契约。
- 删除旧配置字段：先确认迁移和宿主数据兼容，再单独处理。

## 6. 每批次执行流程

1. 先统计目标区域当前生产源码行数。
2. 只改一个独立主题。
3. 为竞态、兼容性或安全行为补短注释和必要测试。
4. 运行 `yarn ts7 --noEmit`、相关测试、`yarn check` 或 `yarn build:client`。
5. 确认生产源码净减少后提交。
6. 提交格式：`refactor: 中文描述`。
7. 如果净增或行为风险无法证明，撤销该批次，不提交。

## 7. 最终目标

短期目标：在不删除功能和公共契约的情况下，服务端和客户端生产源码净减少 **500～1000 行**。

中期目标：通过市场状态合并和持久化原语，争取净减少 **1000～1800 行**。

不把“拆成更多文件”“增加接口”“增加注释”计为精简收益。最终验收必须同时看：

- 生产源码行数
- 单文件最大行数
- 测试通过率
- RPC/DataService/HTTP 契约
- 宿主 dev/prod 冒烟结果
