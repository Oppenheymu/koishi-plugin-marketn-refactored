# 性能优化报告:插件市场与依赖页滚动渲染

> 2026-08 · 针对「页面上下来回滚动掉帧」的专项优化。允许破坏性重构,本文档
> 是本次改动的完整记录与验收依据。

## 背景与瓶颈定位

两个页面的滚动掉帧根因不同,经代码审查定位如下:

### 插件市场页(/market)

页面已有一套自实现虚拟滚动(spacer 占位 + 可视窗口切片 + rAF 合并),滚动
本身的调度开销不大;真正的瓶颈是**卡片进入视口时的挂载成本过高**:

| 开销源 | 原状 | 问题 |
| --- | --- | --- |
| `k-markdown` | 每卡一个实例渲染 description | markdown 解析 + 组件树创建,单卡最大开销 |
| `el-tooltip` | 每卡 2 + N 个(N=作者数) | 每个都带 popper 组件树,快速滚动时新卡批量创建 |
| overscan | 3 行 | 挂载成本高时预渲染缓冲不足,快滚露底 |

### 依赖页(/dependencies)

页面**完全没有虚拟化**:几百张卡片全量渲染,每张卡片又是重组件:

1. **全量 DOM 的 layout/paint**:数百卡 × 每卡几十个节点,滚动时整个长列表
   参与排版与绘制,这是滚动掉帧的直接原因。
2. **每卡挂 3 个对话框子组件**(忽略更新/本地绑定/合包卸载),从不打开也
   常驻组件树:几百卡 × 3 = 上千份组件 setup。
3. **版本下拉全量渲染 el-option**:`analyzeVersions` 返回全部版本(几十个),
   每版本一个 el-option 组件常驻,单卡几十个。
4. **registry 推送整表替换**:服务端批量拉取元数据期间逐包推送
   `market/registry` / `market/registry-status`,客户端每次
   `store.registry = { ...store.registry, ...data }` 整表换引用 →
   全部卡片的 `analyzeVersions`/状态 computed 失效 → **拉取期间连续全列表
   重渲染**,叠加在滚动上表现为持续掉帧。

## 技术要点

### content-visibility: auto(依赖页滚动核心修复)

CSS 标准的「跳过视口外渲染」:视口外的卡片跳过 layout/paint/style 计算,
由 `contain-intrinsic-size: auto 13rem` 提供占位高度——`auto` 关键字让
浏览器**记住每张卡上次渲染的实际高度**,首次滚过时高度从估算值收敛,
之后滚动条稳定。这是社区(w3c/web.dev/Chrome 团队)对「已有大量 DOM 的
长列表」的标准做法,相比把可变高度卡片墙改造成 JS 虚拟滚动,侵入最小、
零数据层风险。

已知权衡:首次快速滚过未渲染过的卡片时,滚动条可能有轻微高度调整
(估算 13rem → 实际高度),换取的是视口外卡片零渲染成本。

选择卡片级而非分组级粒度,配合已有的分组折叠(v-if),视口内只保留
真正可见的渲染工作。

### 原地逐 key 合并(响应式失效范围收缩)

原来 `{ ...store.registry, ...data }` 每次推送创建新的顶层引用,所有读取
`store.registry` 的 computed 全部失效。改为逐 key 原地赋值后,Vue 的
属性级依赖精确生效:每张卡片只订阅自己的包名 key,**推送只让被更新包的
卡片重算**。页面级 `items` 分类 computed 仍会在推送时重算(分类视图本质
依赖所有包的状态),由微批把连续推送收敛。

### 微批(50ms 窗口)

批量拉取期间服务端逐包推送(一个包 loading→done 至少两路),微批窗口把
短时间内的多路推送合并成一次应用、一次 `items` 重算;同一包后到的状态
自然覆盖先到的。`market/registry-status/clear` 会丢弃未应用的缓冲并取消
定时器,保证「重新开始拉取」语义干净。

### 版本下拉懒渲染

`el-select` 的 popper 默认常驻,el-option 组件与 DOM 全量存在。改为首次
`visible-change(true)` 后才渲染版本列表;未打开时 select 直接显示当前值
文本(版本场景 value 即显示文本,无 label 缺失问题),`remove` 项在
pendingRemove 态保持常驻以正确显示「移除」文案。

### 对话框单例化

三个对话框从每卡一实例改为页面级单例:卡片只 emit
`open-ignore` / `open-binding` / `open-bundle-uninstall`(payload 为包名),
`use-dependency-dialogs` 持目标包状态,`v-if` 挂载 + `nextTick` 后调
`open()`(打开时初始化预设的语义保持不变)。数百卡 × 3 份组件 setup
归零。

## 验证

- `yarn check` 通过(131 文件受检;两条 size 警告为既有 src 文件,非本次改动)
- `yarn build` 通过(tsdown + client,`style.css` 产物名保持)
- `yarn test` 1024 例全部通过(含新增 registry-state 5 例)

预期收益(供实测对照):

- 依赖页滚动:视口外卡片不再参与 layout/paint,滚动帧成本从 O(全部卡片)
  降为 O(可见卡片);
- 依赖页批量拉取期间:推送应用从「每包一次全列表重渲染」降为「50ms 一次
  增量更新」;
- 市场页滚动:新卡进入视口的挂载成本大幅下降(无 markdown 解析、无 popper
  组件树),overscan 4 行提供更充裕的预渲染缓冲。

## 后续可选方向(未实施)

- 依赖页若未来卡片数上千,可再评估 JS 虚拟滚动(content-visibility 的
  DOM 常驻内存仍是 O(N),只是渲染成本跳过);
- 市场页 action 插槽的 `el-button` 可再降级为轻量按钮,当前不是主要矛盾;
- `expandedDependency` 展开时的全卡片 `editing` 重算是点击时刻的一次性
  成本,暂不处理。
